
# Automation & Deployment

```
본 문서는 Streamlit 기반 데이터 파이프라인 자동화 및 배포 구조를 정의합니다.

본 프로젝트는 데이터 분석 환경 설계(MySQL)와
사용자 실행 환경(Streamlit + SQLite)을 분리하여 설계되었습니다.

초기에는 데이터 모델링과 KPI 재현성을 중심으로
Raw → Staging → Data Mart → Analytics Layer 구조를 설계하였으며,

이후 사용자가 별도의 환경 설정 없이 데이터를 업로드하고
전체 분석 파이프라인을 실행하여 대시보드를 통해 결과를 직접적으로 확인할 수 있도록
SQLite 기반 경량 실행 환경과 Streamlit 인터페이스를 구축하였습니다.

이를 통해 설계 관점의 데이터 구조 정합성과
실행 관점의 접근성 및 재현성을 동시에 확보하는 것을 목표로 합니다.
```


---

## 1. 설계 전략

```
본 프로젝트는 데이터 분석 설계와 사용자 실행 환경의 목적이 다르다고 판단하여
DB 및 실행 구조를 분리하는 전략을 채택하였습니다.

초기 설계 단계에서는 데이터 모델링과 KPI 재현성 확보를 중심으로 
MySQL 기반 환경에서 Raw → Staging → Data Mart → Analytics Layer를 구성하였습니다.

이 과정에서 데이터 정합성, 레이어 간 역할 분리, 분석 로직의 명확한 구조를 
우선적으로 고려하였습니다.

이후 사용자 관점에서는 별도의 데이터베이스 환경 구축 없이
데이터 업로드만으로 분석 결과를 확인할 수 있는 실행 환경이 필요하다고 판단하였으며,

이를 위해 SQLite 기반 경량 DB와 Streamlit 인터페이스를 결합하여
자동화된 데이터 파이프라인을 구성하였습니다.

즉, 본 프로젝트는 다음과 같은 기준으로 설계되었습니다.

- 설계 단계: 구조적 정합성과 확장성을 중심으로 MySQL 사용
- 실행 단계: 접근성과 실행 편의성을 중심으로 SQLite 사용
  
이를 통해 데이터 분석 설계 역량과
실사용 가능한 자동화 환경 구축을 동시에 달성하는 것을 목표로 합니다.
```


### 1.1 설계 목표

```
본 단계의 목표는 기존 MySQL 기반 데이터 분석 파이프라인을 유지하면서,
사용자가 직접 실행할 수 있는 자동화 및 배포 환경으로 전환하는 것입니다.

이를 위해 원본 데이터 업로드부터 데이터 적재, SQL 파이프라인 실행,
분석 결과 조회 및 시각화까지의 전체 흐름을 Streamlit 환경에서
일관되게 실행할 수 있도록 구성합니다.

또한 배포 환경에서는 SQLite 기반의 경량 실행 구조를 적용하여
별도의 데이터베이스 설정 없이도 동일한 분석 흐름을 재현할 수 있도록 설계합니다.
```

- **핵심 목표: 기존 분석 구조 유지 + 실행 가능한 자동화/배포 환경 구축**
	- 설계 환경: MySQL 기반 분석 파이프라인 유지 (데이터 모델링 및 KPI 로직 보존)
	- 실행 환경: SQLite + Streamlit 기반 자동화 및 배포 환경 구성 (사용자 설치 없이 실행)


### 1.2 변경 범위

```
자동화 및 배포 환경 구축을 위해 기존 MySQL 기반 파이프라인에서
실행 환경과 관련된 영역을 중심으로 구조를 변경합니다.

본 단계에서는 분석 로직 자체를 수정하지 않고,
데이터 적재 방식, 데이터베이스 구조, 실행 방식 등
파이프라인의 실행 환경을 SQLite 기반으로 전환하는 데에 초점을 둡니다.

변경 내용은 다음과 같습니다.

- 데이터 적재 방식 변경
- 데이터베이스 구조 변경
- SQL 실행 방식 변경
- 데이터 접근 방식 변경
- 실행 흐름 통합
```

- **데이터 적재 방식 변경**
	- MySQL `LOAD DATA INFILE` → pandas 기반 `to_sql()`로 전환
	- 사용자 업로드 파일을 직접 DataFrame으로 변환 후 SQLite에 적재

- **데이터베이스 구조 변경**
	- 다중 schema 구조(raw / stg / dm / am) → 단일 SQLite DB 구조로 통합
	- schema 대신 table prefix 방식 사용 (ex. `raw_orders`, `stg_orders`)

- **SQL 실행 방식 변경**
	- MySQL 서버 기반 실행 → Python 환경에서 SQLite SQL script 실행
	- 전체 파이프라인을 Python에서 순차적으로 제어

- **데이터 접근 방식 변경**
	- CSV 파일 기반 결과 조회 → SQL Query 기반 직접 조회
	- Streamlit에서 DB 결과를 바로 시각화에 사용

- **실행 흐름 통합**
	- 데이터 적재, SQL 실행, 결과 조회 과정을 Streamlit  앱 내에서 일괄 처리
	- 사용자 입력을 파일 업로드 중심으로 단순화


### 1.3 유지 범위

```
본 단계에서는 자동화 및 배포를 위한 실행 환경만 변경하며,
기존 데이터 분석 구조와 로직은 변경하지 않습니다.

이를 통해 기존 분석 결과의 정합성, KPI 재현성, 기존 환경에서의 파이프라인 재현성을 유지합니다.

유지 범위는 다음과 같습니다.

- KPI 정의 및 계산 로직 유지
- Analytics Layer SQL 유지
- BI View 구조 유지
- 데이터 모델 구조 유지
  
즉, 자동화 및 배포를 위해 기존 MySQL 환경에서의 분석 로직과 설계는 유지하고, 
실행 환경만 변경하여 로컬 환경과 배포 환경 간 동일한 분석 파이프라인을 유지합니다.
```

- **KPI 정의 및 계산 로직 유지**
	- Revenue, Orders, Active Buyers, AOV, ARPB 등 핵심 KPI 계산 방식 유지
	- 기존 SQL 기반 KPI 산출 로직 변경 없음

- **Analytics Layer SQL 유지**
	- Growth Structure, Growth Drill Down, Customer Value Structure, Operational Stability
	- 분석 모듈의 SQL 구조 및 로직 그대로 유지

- **BI View 구조 유지**
	- 분석 결과 제공을 위한 View 구조 유지
	- 시각화에 사용되는 데이터 형태 변경 없음

- **데이터 모델 구조 유지**
	- Raw → Staging → Data Mart → Analytics 레이어 구조 유지
	- Fact / Dimension 기반 데이터 모델링 구조 유지


### 1.4 실행 흐름

```
자동화 환경은 사용자의 최소한의 입력으로 전체 데이터 파이프라인이 실행되도록 설계합니다.

사용자는 원본 데이터를 업로드하는 것만으로
데이터 적재부터 분석 결과 시각화까지의 전 과정을 수행할 수 있습니다.

전체 실행 흐름은 다음과 같습니다.

1. 데이터 업로드
2. SQLite DB 생성
3. Raw 데이터 적재
4. SQL 파이프라인 실행
5. 결과 데이터 조회
6. 시각화
```

- **데이터 업로드**
	- 사용자가 CSV 파일 업로드
	- 업로드된 파일을 pandas DataFrame으로 변환

- **SQLite DB 생성**
	- 실행 시점에 SQLite 데이터베이스 생성
	- 기존 DB가 존재할 경우 초기화 옵션

- **Raw 데이터 적재**
	- DataFrame → SQLite 테이블로 적재 (`to_sql`)
	- 테이블명은 prefix 기반으로 생성(raw_*)

- **SQL 파이프라인 실행**
	- Staging → Data Mart → Analytics → BI View 순으로 SQL 실행
	- Python에서 SQL script를 순차적으로 실행하여 전체 구조 생성

- **결과 데이터 조회**
	- BI View 기준으로 분석 결과 조회
	- pandas `read_sql_query`를 통해 데이터 로드

- **시각화**
	- Streamlit 컴포넌트를 활용하여 KPI 및 차트 출력
	- 데이터 변경 시 자동 반영

## 2. 자동화 및 배포 아키텍쳐

```
본 프로젝트의 자동화 및 배포 환경은
사용자가 원본 데이터를 업로드하면 별도의 환경 설정 없이
전체 데이터 파이프라인을 실행하고 분석 결과를 확인할 수 있도록 구성되어 있습니다.

이를 위해 데이터 적재, SQL 파이프라인 실행, 분석 결과 조회 및 시각화 과정을
하나의 흐름으로 통합하고,
Streamlit과 SQLite를 기반으로 경량 실행 구조를 설계하였습니다.

특히 기존 MySQL 기반 분석 구조를 유지하면서,
배포 환경에서도 동일한 분석 흐름과 결과를 재현할 수 있도록
실행 구조를 단순화하고 자동화하는 데에 초점을 두었습니다.
```


### 2.1 전체 구조

```
본 자동화 환경은 사용자 입력부터 분석 결과 출력까지의 전 과정을
하나의 흐름으로 연결한 구조로 설계되어 있습니다.

사용자는 원본 데이터를 업로드하는 것만으로
데이터 적재, SQL 파이프라인 실행, 분석 결과 조회 및 시각화까지의
전체 과정을 수행할 수 있습니다.

전체 구조는 다음과 같습니다.

[User]
  ↓
[Streamlit Application]
  ↓
[SQLite Database]
  ↓
[SQL Pipeline (stg → dm → am → bi)]
  ↓
[Visualization Dashboard]
```

- **User**
	- CSV 파일 업로드를 통해 데이터 입력

- **Streamlit Application**
	- 전체 파이프라인 실행 제어 (데이터 적재, SQL 실행, 결과 조회)
	- 사용자 인터페이스 제공

- **SQLite Database**
	- 단계별 SQL 스크립트를 실행하여 데이터 변환 및 KPI 계산 수행

- **Visualizatoin Dashboard**
	- 분석 결과를 KPI 및 차트 형태로 시각화
	- 데이터 변경 시 결과 자동 반영


### 2.2 데이터베이스 구조

```
본 자동화 환경에서는 SQLite 기반 단일 데이터베이스를 사용하여
전체 파이프라인을 구성합니다.

기존 MySQL 환경에서 사용하던 다중 schema 구조(raw / stg / dm / am)를
SQLite 환경에 맞게 단일 DB 내 table prefix 방식으로 재구성하였습니다.

이를 통해 레이어 구조를 유지하면서도 
경량 실행 환경에 적합한 데이터베이스 구조를 구현하였습니다.

데이터 베이스 구조는 다음과 같이 구성됩니다.

- raw_* (기존 raw 레이어)
- stg_* (기존 stg 레이어)
- dm_* (기존 dm 레이어)
- am_* (기존 am 레이어)
- bi_* (기존 bi 레이어)
  
테이블 및 View 명명 규칙은 다음과 같습니다.

- 레이어 구분을 위해 prefix 사용
	- ex. raw_orders, stg_orders, ...

- 분석 흐름에 따라 단계별로 데이터 생성
	- raw → stg → dm → am → bi

이를 통해 SQLite 환경에서도 기존 데이터 레이어 구조를 유지하여
분석 로직의 일관성과 확장성을 확보합니다.
```

- **raw_***
	- 원본 데이터 적재 테이블
	- CSV 업로드 데이터를 그대로 저장

- **stg_***
	- 데이터 정제 및 전처리 테이블
	- 데이터 타입 정리 및 기본 변환 수행

- **dm_***
	- 분석 목적의 데이터 모델 (Data Mart)
	- Fact / Dimension 구조로 구성

- **am_***
	- KPI 계산 및 분석용 데이터
	- 집계 및 파생 지표 생성

- **bi_***
	- 대시보드 연결용 데이터
	- 최종 결과를 조회


### 2.3 애플리케이션 구조

```
본 자동화 환경은 Streamlit 기반 애플리케이션을 중심으로
데이터 적재, SQL 파이프라인 실행, 결과 조회 및 시각화를 통합하여 구성합니다.

애플리케이션은 사용자 입력을 시작으로 데이터 처리와 분석 결과 출력까지의 전 과정을
하나의 흐름으로 제어하는 역할을 수행합니다.

애플리케이션은 다음과 같은 구조로 구성됩니다.

- 입력(Input Layer)
- 데이터 처리(Data Processing Layer)
- 데이터 조회(Data Access Layer)
- 출력(Output Layer)

전체 파이프라인은 Python 코드에서 순차적으로 제어되며,
각 단계는 독립적인 함수로 구성됩니다.

주요 실행 흐름은 다음과 같습니다.

- 데이터 업로드
- DB 생성 및 초기화
- Raw 데이터 적재
- SQL 파이프라인 실행
- 결과 데이터 조회
- 시각화 출력

애플리케이션은 다음과 같이 역할을 분리하여 구성합니다.

- SQL
- Python
- Streamlit

이를 통해 SQL 기반 분석 로직과 Python 기반 실행 제어를 분리하여
구조적 명확성과 실행 효율성을 동시에 확보합니다.
```

#### 애플리케이션 구조

- **입력**
	- 사용자 CSV 파일 업로드
	- 업로드된 데이터를 DataFrame으로 변환

- **데이터 처리**
	- SQLite DB 생성 및 초기화
	- Raw 데이터 적재(`to_sql`)
	- SQL 파이프라인 실행 (stg → dm → am → bi)

- **데이터 조회**
	- BI View 기준 데이터 조회(`read_sql_query`)
	- 분석 결과를 DataFrame 형태로 로드

- **출력**
	- KPI 및 차트 시각화
	- Streamlit 컴포넌트를 활용한 대시보드 구성

#### 역할 분리

- **SQL**
	- 데이터 변환 및 KPI 계산 로직 담당

- **Python**
	- 파이프라인 실행 제어 및 데이터 입출력 담당

- **Streamlit**
	- 사용자 인터페이스 및 시각화 담당

## 3. 배포 구조

```
본 자동화 환경은 사용자가 별도의 데이터베이스 설정이나 로컬 개발 환경 구성 없이
웹에서 직접 데이터 업로드와 분석 결과 확인이 가능하도록 배포하는 것을 목표로 합니다.

이를 위해 GitHub를 통해 소스 코드를 관리하고,
Streamlit Community Cloud를 활용하여 애플리케이션을 배포합니다.

배포 환경에서는 SQLite 기반 경량 데이터베이스를 사용하여
```

### 3.1 배포 환경 및 방식

```
본 자동화 환경의 배포는 GitHub와 Streamlit Community Cloud를 기준으로 구성합니다.

소스 코드는 Github 저장소에서 관리하며,
배포 환경에서는 Streamlit Community Cloud가 해당 저장소를 기반으로
애플리케이션을 실행합니다.

배포 환경에서는 SQLite 기반 경량 데이터베이스를 사용하여 
별도의 데이터베이스 서버 없이도 전체 분석 파이프라인이 동작할 수 있도록 구성합니다. 

사용자는 웹 페이지에 접속하여 별도의 설치 없이 데이터 업로드와 분석 결과 확인이 가능합니다.

배포 흐름은 다음과 같습니다.

- 코드 관리
- 배포 연동
- 애플리케이션 실행
- 사용자 접근
  
해당 자동화의 실행 특징은 다음과 같습니다.

- 별도 데이터베이스 서버 불필요 (SQLite 사용)
- 사용자 로컬 환경 설정 불필요
- GitHub 코드 변경 시 배포 환경 자동 반영
```

#### 배포 흐름

- **코드 관리**
	- GitHub 저장소에 프로젝트 코드 업로드 및 관리

- **배포 연동**
	- Streamlit Community Cloud에서 GitHub 저장소 연결
	- 실행 파일 기준으로 애플리케이션 실행

- **애플리케이션 실행**
	- Cloud 환경에서 자동으로 필요 파일(`reuqirements.txt`) 설치
	- Streamlit 앱 실행

- **사용자 접근**
	- 웹 URL을 통해 애플리케이션 접속
	- 데이터 업로드 → 파이프라인 실행 → 결과 확인
